# A personal opinion on the Zig programming language

**TL;DR:** [The Zig programming language](http://ziglang.org/) is amazing and it
really feels as _"a better C"_ as its author promised. However, it is still not
production-ready and has some rough edges to polish. This blog post will
describe my personal experience and feelings during the development of a small
videogame in Zig.

Few months ago I got trapped into the [Zig hype](http://ziglang.org/) and
decided to give a try because I felt very appealing its promised C interoperability
and its efficiency. And they didn't lie!

I wrote a simple videogame in Zig and [Raylib](https://github.com/raysan5/raylib).
If you want to see how the final result was, have a look at the link below!

## When Zig is **really a better C**

Zig has learnt from languages like Go and Rust, and ships its own toolset that
standardizes code formatting, resolution of external dependencies and project
structure. I've easily moved my project from one computer to another and I just
needed to install a single tool: the `zig` CLI.



- Bundling build system and project structure.
- No undefined behaviors nor compiler-dependent behaviors.
- Integrating with an external C dependency is as simple and straightforward that is even simpler than it would be in C. Especially if the C dependencies use `build.zig`.

## Rough edges
- Zig maths are a hell!!
- Aun muy inmaduro. Cosas como DoublyLinkedList parecen muy exoticas
- lack of runtime errors. We shouldn't be forced to check "out of memory" error e.g. each time we allocate memory.
- problemas con null checks de optional pointers

## Why Zig is not production-ready:
- Zig IDE integration is still rough (VSCode >> IntelliJ)
- Error sometimes compiled incorrect code. Could point them as "black holes" in my debugging session and hardcoded there other explicit operations.

- doublylinkedlist es un poco exotico
- no es estable aun: problemas cuando los punteros se vuelven complejos.

- type casts is so painful that you end up using if-else chains for simple things that could have been
  solved via integer operations. Even you manually unroll loops.

Me ha gustado muchos typechecks en runtime, como completud de switches, error on variable shadowing...

Initially did a "super-optimization" approach with u8, i8, u16, i16... but WASM-emscripten did not like it and had a lot of bugs/glitches.
Even after replacing all the `u*` by isize and `i*` by isize, got some glitches. Choose to use isize everywhere and add  in array indices and loops (usize mandatory).
So I would not use it for embedded devices that rely on tiny memories or word lengths
